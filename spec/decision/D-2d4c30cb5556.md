title: Scope of release 3
rationale: "The recheck showed that core requirements mixed criteria for the Halcyra HC-4 and the Halcyra HC-2, so that no build could check every criterion, and that a test result without a criterion counted for every criterion of its requirement. ReqSeq has no validity per acceptance criterion: a criterion that holds only in the HC-2 build needs a requirement of the variant. One test per criterion and view therefore needs more system requirements than the limit of the project allows; merging requirements instead would break the rule of one behaviour per requirement. The missing glossary terms were findings of the recheck."

Release 3 corrects the specification and the evidence of release 2 after the recheck with ReqSeq 0.14, with the client's decisions of release 3 (offline date of the aircraft data, a total mass below the envelope, the planned fuel burn named with the landing result). The record of the check stays deferred: it is needed before the app is used regularly with students, and the open field validation comes before that. It amends [Scope of release 2](reqseq:2f23eb42-057f-44ec-88cd-10a960b70292?version=n2:3b5d2ed04bb7dd58): items 1 to 4 and 6 of that decision and its deviation on the approval of new or changed requirements stay valid; item 5 and its evidence gate are replaced here.

HC-2 replacement requirements (instead of item 5 of the scope of release 2):

1. An acceptance criterion of a core requirement names either a situation that both builds can show (a neutral criterion) or values of the Halcyra HC-4. A neutral criterion is checked in the core build and in the HC-2 build, each by a test named with the same criterion key.
2. A core requirement with a criterion that names values of the Halcyra HC-4 is replaced in the variant [Halcyra HC-2](reqseq:05ae9286-bea0-45ad-9338-d1f959f23826?version=n2:22b0303ec030d854) by a requirement of the variant (relation `replaces`, validity Halcyra HC-2, package Variant Halcyra HC-2) with the statement of the core requirement and acceptance criteria with values from the type data of the Halcyra HC-2.
3. A test names exactly one acceptance criterion, `[SR-…/AK-<criterion key>]`, or for a Rust test `sr_<short id>_ak_<criterion key>_…`. A test that names a requirement without a criterion is no evidence.

Evidence gate (instead of the evidence gate of the scope of release 2): the CI job `evidence` reads only the enriched test results of its own run. It fails when a test result names a requirement without an acceptance criterion, and when a system requirement that is not obsolete lacks a passed test result at its current version for one of its acceptance criteria, in the core view or in the view of the Halcyra HC-2. Draft requirements are gated too: release 3 delivers specification, code and tests in one change.

Limits of the project exceeded by this release (counted as [Counting of the project limits](reqseq:366f6088-ab59-44cd-9819-da26dc1c8553?version=n2:cb4596715e213aa7) says):

- System requirements: at most 76 in both workspaces together instead of 50. This workspace has 66, of which 25 are replacement requirements of the Halcyra HC-2; the supplier's workspace has 10.
- Glossary terms: at most 26 in this workspace instead of 20, for the terms that the requirements and needs use and the glossary lacked: fleet data file, report time, type data, limit check rule, HC-2 build, weighing date and seat row.
