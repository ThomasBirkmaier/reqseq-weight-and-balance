Release 2 completes the product. It replaces the scope decisions of release 1 ([Release 1 checks the loading without fuel](reqseq:09b067c4-bd9a-447b-9208-071791d192b3?version=n1:737df016c5876bfb), [Scope of run 1](reqseq:0949deaf-3bdb-4aca-8f67-511a39083f2b?version=n1:dbc46960aff90f59)).

Product:

1. The Halcyra HC-4 is the core product. The Halcyra HC-2 stays the variant of the core: a separate build of the app below `hc2/` for an HC-2 fleet.
2. Fuel is part of the loading: the usable fuel at take-off, prefilled with the quantity the fuel system module reports for the selected aircraft and correctable by the pilot, and the planned fuel burn, from which the app checks the landing. The positive limit indication is "Within limits"; the note "Fuel is not included in this version." is removed.
3. Fuel density, fuel lever arm, usable fuel capacity and the reported fuel quantity come from the fuel interface data file of the supplier (`data/fuel-module.json`), never from a type data decision. This workspace names requirements of the supplier only by ID, version and repository name (`fuel`); no title or text of the supplier enters this repository.
4. The type data name no maximum landing mass of their own: the landing mass is compared with the maximum take-off mass, and the centre of gravity at landing with the envelope, by the same limit check rule as at take-off.
5. The HC-2 is complete when it has the fuel path with its own fuel data and every core requirement that applies in its view is verified there by automated end-to-end tests of the HC-2 build, enriched for the variant (instead of the hand-written HC-2 records of release 1). A test of the HC-2 build checks an acceptance criterion of a core requirement with the same Given, When and Then, with the aircraft HC2-01 and the values recomputed from the type data of the HC-2; it is named `[SR-…/AKn] HC-2: …` only when it checks that criterion so. A test that checks the statement of the requirement with other values is named `[SR-…] HC-2: …` without a criterion, so that no variant record claims a criterion it did not check.
6. The notices "Invented aircraft. Not for flight operations." and "This app is an aid. The pilot in command remains responsible for mass and balance according to the flight manual." stay.

Deferred, outside the scope of run 2: a record of the check with aircraft, date, entries and result (client remark from release 1, priority could). It stays a draft need; no requirement derives from it.

Evidence gate: the CI job `evidence` reads the evidence of its own run after enrichment and fails when an approved system requirement has no passed test result at its current version, in the core or in the variant view (`reqseq evidence degree`, share 1 per view, selection status approved). Draft requirements are not gated, so that a specification pull request can be merged before the code exists. Deviation from the project procedure, which has IV&V approve a requirement before code: IV&V releases each new or changed requirement for implementation in its review file before code, naming the requirement with its version, and sets the status approved only after the implementation pull request, together with its verification; the approval commit names the same version. The auditor sees the release in the review file and the approval in the commit. Reason: the required evidence gate cannot pass for an approved requirement whose code does not exist yet.


Limits: the limits of the project for stakeholders, needs, hazards, decisions and glossary terms count per workspace (this one and the supplier's); the limit for system requirements counts both workspaces together.
